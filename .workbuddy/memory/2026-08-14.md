# 2026-08-14 IB-PTM7330 多指令集适配

## 背景
- IB-PTM7330 便携式热转印打印机到货，厂家提供了《位图方式打印命令说明文档》
- 标签纸 50x30mm，需要适配多种指令集打印机
- 在现有 Zebra ZPL 适配基础上，扩展为多指令集架构

## 架构设计
- **printerConnection.js** — 通用蓝牙 SPP 连接层，与指令集无关
  - 连接、断开、发送文本/字节、读取响应
  - `sleep` 导出供适配器使用
- **printerAdapter.js** — 适配器基类与工厂
  - `PrinterAdapter` 基类：connect/disconnect/printTest/printTemplate/printText/queryFonts 等
  - `createAdapter(protocol)` 工厂：动态 import 对应适配器
  - `detectProtocolByName(name)` 按蓝牙名自动推断协议
  - `DEFAULT_LABEL`: 50x30mm @ 300dpi
- **printerManager.js** — 统一入口
  - 按 protocol 创建对应 Adapter，单例共享连接
  - `_ensureConnected()`: 未连接时自动连默认打印机
  - `printWithSaved(zpl)`: 兼容旧 API，自动连接 + 发送 ZPL
  - `printTemplate(tpl, data)`: 自动连接 + 通过适配器打印模板
- **adapters/zebraAdapter.js** — Zebra ZPL/CPCL 适配器
  - 从旧 zebraPrinter.js 迁移全部 ZPL 逻辑
  - connect 后自动验证(~HS) + 异步检测 CJK 字体
  - printTemplate 传入字体状态给 buildZpl
- **adapters/ibptm7330Adapter.js** — IB-PTM7330 ESC/POS 位图适配器
  - Android Canvas 渲染文本(含中文) → 二值化 → ESC/POS 位图命令
  - 命令格式: `1B 40` 初始化, `1F 27 01 n 88` 设宽度, `1F 2A` 打印行, `1F 2B` 压缩前导空白, `1F 2E` 重复行, `0C` 走纸

## zebraPrinter.js → 兼容 shim
- 旧文件改为透明转发 shim，所有方法透传到 printerManager + printerConnection
- 3 个业务文件 import 从 zebraPrinter.js 改为 printerManager.js:
  - `components/mes/print/snPrintList.vue`
  - `pages/print/labelTemplate.vue`
  - `pages/print/labelImport.vue`
- snPrintList.vue / labelTemplate.vue / labelImport.vue 中 `printWithSaved(buildZpl(...))` 改为 `printTemplate(tpl, data)`，让适配器自动传字体状态

7. **Zebra 专用卡片对 IB-PTM7330 也显示**: 加 `v-if="protocol === 'zebra'"` 条件

# 2026-08-14 (下午) IB-PTM7330 BLE 连接修复

## 问题
- 用户反馈点击"IB-PTM7330 位图测试"和"中文文本测试"一直卡在"位图渲染中..."弹窗
- 用户提供之前和 DeepSeek 的对话，揭示了关键信息：**IB-PTM7330 是 BLE 设备，不是经典蓝牙 SPP！**

## 根因分析
1. **BLE vs SPP**: printerConnection.js 只支持经典蓝牙 SPP (UUID 00001101)，而 IB-PTM7330 是 BLE GATT 设备
   - BLE Service UUID: 0000FF00-0000-1000-8000-00805F9B34FB
   - Write Characteristic: 0000FF02-0000-1000-8000-00805F9B34FB
   - Notify Characteristic: 0000FF01-0000-1000-8000-00805F9B34FB
   - MAC: 60:6E:41:37:FD:62
2. **DPI 争议**: 参数表写 300dpi，DeepSeek 脚本按 8 dots/mm (≈203dpi) 生成数据，需要实测验证哪个更准

## 修复内容

### printerConnection.js — 添加 BLE GATT 连接支持
- 新增 BLE 常量（Service/Write/Notify UUID）
- 新增 BLE 状态变量（bleConnected, bleDeviceId, bleWriteChunkSize）
- `bleOp(apiName, params)` — 通用 uni.* BLE API Promise 包装
- `connectBLE(address, name)` — 完整 BLE 连接流程：openAdapter → createConnection → 发现服务 → 发现特征值 → 协商 MTU
- `sendBytesBLE(bytes)` — 分包发送：按 MTU chunk size 拆分，每包 5ms 延迟防溢出
- `disconnectBLE()` — 关闭 BLE 连接
- `connect(address, name, type)` — type='ble' 走 BLE，默认走 SPP
- `isConnected()` / `disconnect()` / `getCurrentPrinter()` — 兼容 BLE 和 SPP
- `sendBytes(bytes)` — BLE 返回 Promise(异步写)，SPP 同步写；调用方统一 await

### printerAdapter.js
- `PrinterAdapter` 基类新增 `connectionType = 'spp'` 字段
- `connect()` 传递 `this.connectionType` 给 `conn.connect()`
- `DEFAULT_LABEL.dpi` 初始 300 → 改为 203（8 dots/mm）→ 最终按参数表改回 300

### ibptm7330Adapter.js
- `connectionType = 'ble'`（使用 BLE 连接）
- `dpi` 改为 300（按参数表），如实测打印尺寸不对可回调到 203
- 全链路 console.log 日志（TAG = `[Ibptm7330]`）：
  - printTest/printTextLines 的每一步（渲染开始/完成、发送进度）
  - buildTestLabelCommands（createBitmap/Canvas/drawText/各步骤）
  - bitmapToEscPos（像素扫描耗时、black/white 计数、命令打包耗时）
- `conn.sendBytes(chunk)` 改为 `await conn.sendBytes(chunk)`（兼容 BLE 异步写）
- 位图渲染：先尝试 `Bitmap.getPixels()` 批量读取，实测在 5+ runtime 上卡死；后改为 `copyPixelsToBuffer + Base64 + uni.base64ToArrayBuffer`，一次性取图避免 N 次 JNI
- `clearBuffer`/`calibrate` 也改为 `await conn.sendBytes()`

### printSetting.vue
- `connectDevice` / `testIbptm7330` / `testIbptm7330Text` 添加 console.log
- 连接和测试的 error 也输出到 console.error

## 2026-08-14 16:42 位图像素读取崩溃修复
- 错误：`base64ToArrayBuffer:fail parameter 'base64'. Expected String with value "null", got Null`
- 根因：`readBitmapPixels` 用的 `copyPixelsToBuffer + Base64.encodeToString + uni.base64ToArrayBuffer` 方案，在用户 PDA 的 5+ runtime 上 `Base64.encodeToString` 返回 null（该机型不支持此调用链）
- 修复：改回**逐像素 `getPixel`** 读取（与 `cjkBitmap.js` 验证可用的方式一致），直接二值化为 MSB 在前的行字节，去掉 Base64/ByteBuffer 路径
- 同时删除 `pixelsToRows` 中间函数，`_renderAndTest` / `bitmapToEscPos` 调用点同步更新
- 判黑逻辑与 cjkBitmap 一致：`alpha > 127 && r < 128`
- 注意：300dpi 下 591×354 ≈ 20.9万次 getPixel，可能耗时几秒，已加每 40 行进度日志（不会再"冻死"）
- copyPixelsToBuffer + Base64 取图是否一次成功
- MTU 协商是否生效（影响发送速度）
- 300dpi 下打印效果是否正确（如尺寸偏大再试 203）
