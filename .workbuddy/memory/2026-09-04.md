## 软件更新功能（App 端 `utils/appUpdate.js`）排障收尾

### 现象链（HBuilderX 调试基座真机测试）
- web「App下载」、后端接口均已通（curl 验证 `200 + Content-Length:15794864`，日志 `TenantRequestHandler 获取租户ID` + `PdaAppUpdateController 下载 snApp.apk` 正常）。
- App 端卡在"下载拿到数据但写文件失败"：
  1. `plus.downloader` 指定 `filename:'_doc/snApp.apk'` → 0 字节（14:10/14:18 实测）。
  2. `uni.request+arraybuffer` 能完整收到 15794864 字节，但 `FileWriter.write(ArrayBuffer)` 抛空异常；分块 `write()` 第二次调用也抛。

- HBuilderX 调试基座上 5+ 的 `FileWriter` 整条写路径不可靠（write / writeAsBinary 都不落盘）。
- 用户提示"是不是目录问题，直接在根目录操作" → 指向用原生 Java 直接操作 `_doc` 真实路径。

- 写文件两层兜底：
  1. `writeViaFileWriter`：单次 `writeAsBinary(整包)`，目录 `_doc`→`_downloads` 回退。
  2. `writeViaJava`（兜底）：`plus.android.newObject('java.io.FileOutputStream', file)` + `plus.android.invoke(fos,'write', js数字数组)`（5+ 自动转 byte[]），512KB 一块写 `_doc` 真实路径，写完 `flush/close` + `file.length()` 校验。
- 删除死代码 `moveToDocApk`/`verifyApkFile`/`removeOldApk`/`writeByChunks`/`verifyDownloaded`（上次中断时 `downloadApk` 还引用了不存在的 `verifyDownloaded`，已修）。

### 验证

- 模拟 FileWriter 失败→回退 Java：字节数 15794864 全部落盘，MATCH=true，路径含 snApp.apk。

## 15:17 真机再测：writeAsBinary 卡死（已重写）

### 现象
- `uni.request` 已稳定收到 15794864 字节（日志 `收到，类型=[object ArrayBuffer]，15794864 字节`）。
- 但 `writeViaFileWriter` 的 `writeAsBinary(二进制串)` 卡死：`_doc` 那次 34 秒无果后回退 `_downloads`，`_downloads` 直接挂起——`onwrite`/`onerror` 回调都不触发，Promise 永久 pending，永远走不到 `writeViaJava` 兜底。

### 根因（明确）
- `writeAsBinary` 要把 **1579 万个字符的二进制字符串**喂给 5+ `FileWriter`，5+ 运行时处理这种超大字符串会卡死/超时。这与"调试基座 vs 正式打包"无关，打包也不能保证解决。

### 修复（已落地 `utils/appUpdate.js`）
- **废弃 `uni.request` 取字节 + 手写文件**整条链路，改用 `plus.downloader` 原生流式下载直接落盘到 `_downloads/snApp.apk`。
  - 走独立原生下载服务，不碰 JS 字节拼装、不碰 5+ `FileWriter`，15MB 毫无压力。
  - 之前 `plus.downloader` 写 0 字节的唯一原因是 URL 缺租户参数被 302→403；现在 URL 已带 `tenantId`/`Authorization` 查询参数（`uni.request` 已验证能拿到真实 15794864 字节），同一地址现在可正常落盘。
  - `statechanged` 事件天然提供 `downloadedSize/totalSize` 进度百分比。
- 删除死代码：`writeBufferToFile`/`writeViaFileWriter`/`writeViaJava`/`toBinaryString`。`installApk`/`canRequestInstall`/`openInstallSetting` 不变。
- `downloadApk` 契约不变：仍 resolve 出路径字符串、`onProgress` 仍收 `{progress,text}`；`my.vue` 无需改。
- `node --check --input-type=module` 语法通过。

### 给用户结论
- 不用完整打包 APK 验证：HBuilderX 调试基座改这个 js 后「重新运行到设备」即可（基座热更 wgt），无需出正式包。
- 测试时仍避免切后台。

## 16:01 Web 端下载按钮三问题（已修）

### 现象
- `cc-admin-web/src/layouts/index.vue` 的「App下载」按钮：无反馈、有延迟、多次点击有问题。

### 根因
- 旧 `downloadApp`：`await fetch(...)` + `await resp.blob()` 把整个 15MB 缓冲进内存才 `a.click()`。
  - 缓冲期间界面无反应 → "没有反馈"。
  - 整包缓冲完才弹下载框 → "有延迟"。
  - 无并发锁，连点并发多次 fetch → "多次点击有问题"。

### 修复
- 先发一次 `HEAD` 轻量校验（后端对 HEAD 只回头信息不传 body，几乎无延迟），`!ok` 直接报错提示，避免把 403 页面存成 apk。
- 真正下载改用原生 `<a download>`：`tenantId`/`Authorization` 作为 URL 查询参数带上（与 App 端一致，后端从参数读取，避免 403），浏览器自己流式下载、下载栏自带进度条，前端零缓冲。
- `data` 加 `downloadingApp` 并发锁；按钮加 `:disable` + `:loading`（点一下立刻转圈防连点），`finally` 里 1.5s 后解锁。
- 提示文案改为"已开始下载…请到浏览器下载列表查看进度"。

### 验证
- Web 项目 `npm run dev`（`http://localhost:9668`）热更新即可测；无需重启后端。
