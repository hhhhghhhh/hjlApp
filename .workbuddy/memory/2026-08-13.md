## 蓝牙打印多机型适配方案设计

**背景**：用户引入新设备 IB-PTM7330 便携式热转印打印机，需要从单一 ZPL 方案扩展到多指令集。

**IB-PTM7330 关键参数**：
- 指令集：TPCL + ESC/POS 兼容（与项目现状的 ZPL 不兼容）
- 通信：USB + 蓝牙（SPP，UUID 00001101）
- 分辨率：300dpi
- 打印宽度：80/81mm
- 介质：标签纸（支持间隙/反射式传感器），厚度 0.05-0.2mm
- 特色：RFID 打印（UHF 900MHz / HF 13.56MHz），可选

**现状评估**：
- 项目当前是 ZPL 专用方案，深度适配 Zebra 系
- 通信层只走经典蓝牙 SPP，assertAndroid 写死 Android
- 模板引擎只产 ZPL，业务批量打印只能走 ZPL
- Zebra 原生插件（ZSDK_ANDROID_API.jar 等 11 个 jar）存在但未使用

**方案**：分层解耦，分三阶段落地
- P0（本周）：抽出 Driver 基类 + TpclDriver + sendTpcl，让 IB-PTM7330 能手动发指令
- P1（1 周内）：TpclBuilder + EscposBuilder，业务页切换
- P2（后续）：BLE 通道 + Profile 系统 + 其它指令集

**关键文件位置**：
- utils/zebraPrinter.js（当前）
- utils/zplTemplate.js（当前）
- utils/labTemplate.js（当前）
- api/printApi.js（当前）

## 模板统一方案（用户明确"保留一份模板，打印前按打印机适配"）

**输入**：用户从 CodeSoft 6 解析出 `keySn.Lab` → 简化为 `pdaTemplate` JSON（mm 坐标 + anchor + 变量模板化）。

**确认**：`pdaTemplate` 作为唯一的"指令集无关 IR"（中间表示），运行时按 profile.commandSet 翻译成 ZPL/TPCL/ESC-POS。

**IR 字段统一约定（建议）**：
- 坐标：所有 mm，绝不写 dot
- dpi 字段在 pdaTemplate 中废弃或仅作显示参考（实际用 profile.dpi）
- anchor：每个元素必须明示（top-left/center/...）
- 字体：fontName 用通用名（宋体/Tahoma），运行时由 Builder 查 profile.fontMap 映射到具体指令集字体
- mediaType：从模板移除，由 profile 提供（profile 包含介质信息）
- 变量替换：保留 `{{varName}}` 模板语法，Builder 在生成指令时做替换

**4 大运行时换算**：
1. 坐标换算：xMm × profile.dpi / 25.4 = dot
2. anchor 还原：center → 左上角 = (x - w/2, y - h/2)
3. 字体映射：fontName → 指令集字体代号（profile.fontMap）
4. 变量替换：{{keySn}} → 业务注入的实际值

**示例已验证**：keySn 模板在 IB-PTM7330 (300dpi) 下，1mm = 11.81 dot，QR 码 center(10,5) → 左上角(87,28)，输出 TPCL 指令示意完整。

**待用户确认的点**：
1. anchor 字段是否每个元素都明确（text 当前缺，依赖 alignment=center 间接表示）
2. mediaType 由 profile 还是 pdaTemplate 提供
3. pdaTemplate.dpi 字段是否保留（建议废弃）
4. fontName 是否需要在 IR 里同时存一份通用名

## ZR668 中文打不出来问题诊断

**用户澄清**：ZR668 是斑马便携式打印机（不是佳博）。
- 规格：203dpi，72mm 宽，Link-OS，**ZPL + CPCL 双指令集**
- 跟 ZD410/iMZ 等是同一套 ZPL 链路，理论上现有代码能跑

**根因锁定**：代码 `zplTemplate.js:240` 中文走 `^A@N,h,w,E:GB18030.FNT`，这要求打印机内存里有 `E:GB18030.FNT` 字体文件。**ZR 便携机出厂通常不带中文字体**，工业机（ZT/ZD410）才有。字体缺失时 `^A@` 指令静默失败，中文文本被跳过 → 空白。

**立即验证**：跑 `sendZpl('^XA^HWE:*.FNT^XZ')`（zebraPrinter.js:329 已封装），看回显里有没有 GB18030.FNT / SIMSUN.FNT / ANY*.FNT。没有就是根因。

**三种解决方案**：
1. **下载中文字体**（最稳，一次性）：用 Zebra Printer Setup Utility 通过 USB 把 GB18030.FNT 推到 E: 盘，或用 `~DY` 蓝牙下载（慢，字体几 MB）。下载后代码不用改。
2. **改用位图渲染中文**（不依赖字体，最通用）：前端 canvas 渲染中文 → `^GFA` 发位图。便携机/工业机通吃，未来 IB-PTM7330 也能复用。改动中等。
3. **改用 CPCL + GB18030**（ZR668 专属备用）：走 sendCpcl，便携机的 CPCL 模式通常内置 GB18030 解码。但要写 CPCL 模板生成器。

**推荐**：先验证字体，有就下载（方案 1），不行就走位图（方案 2）。方案 2 是长期方向，跟多机型适配方案是同一条路。

## 位图渲染黑线 bug 修复（第一次尝试失败）

**现象**：用户实测 ZR668 打印中文，打出"一条黑线"。
**第一次修复根因假设**：位图尺寸 144×9 dot（对应 keySn 模板 text 框宽 18mm × 字号 0.88mm @203dpi），全黑。
- `Bitmap.createBitmap(w,h,ARGB_8888)` 初始是**全透明 0x00000000**，R 通道=0
- 二值化逻辑 `r < 128 判黑` 把透明区域全部判成黑点
- `Paint.ascent()/descent()` 返回 float，5+ App 某些版本拿不到值变 NaN
- baseline = NaN → `drawText` 坐标无效 → 文字根本没画上去

**第一次修复措施**：`eraseColor(-1)` 填白、去掉 ascent/descent、measureText 容错、直接传 Java int 颜色、drawText try-catch。

**用户复测结果**：修改前后都是黑条，修复未生效。
**结论**：5+ App `plus.android` 反射 Canvas/Paint/Bitmap 在目标运行环境中不稳定，不应继续依赖。

## 位图渲染方案重写：改用 HTML5 Canvas

**决策**：弃用 Android Bitmap + Canvas 反射，改用标准 HTML5 Canvas（`document.createElement('canvas')` + `getContext('2d')` + `getImageData`）。uni-app 页面运行在 webview 中，DOM Canvas 完全可用，稳定且跨平台。

**重写文件**：`utils/cjkBitmap.js`
- 删除所有 `plus.android` 相关代码
- 用 `document.createElement('canvas')` 创建离屏 canvas
- `ctx.measureText` 做断行，`ctx.fillText` 绘制白底黑字
- `getImageData` 读取 RGBA 像素，`R<128` 二值化
- 输出 ZPL `^GFA` 十六进制位图指令
- `isBitmapSupported()` 改为检测 `typeof document !== 'undefined'`

**关键注意点**：
1. 设置 `canvas.width/height` 会重置 context，之后必须重新设置 `font`、`textBaseline`、`textAlign`
2. 字体 fallback 链：`"SimSun", "宋体", "Noto Sans CJK SC", "Source Han Sans SC", "Microsoft YaHei", sans-serif`，确保中文可显示
3. `textBaseline = 'top'`，y 坐标直接用行顶
4. `imageSmoothingEnabled = false` 减少抗锯齿，二值化阈值处理灰边

## 位图全黑 bug 第四次修复（alpha 通道判断）

**用户复测**：Android 反射方案打出"区域全部黑色"（黑条/黑块），说明位图全黑。

**根因**：二值化逻辑只判 R 通道 `(pixel >> 16) & 0xFF`，透明像素（0x00000000）R=0 被判黑。不管 drawColor 填白是否生效，这个判断本身就有问题。

**修复**（`utils/cjkBitmap.js`）：
1. 二值化改成 alpha + R 双判断：`alpha > 127 && r < 128` 判黑
   - 透明(0x00000000): alpha=0 → 白 ✓
   - 黑字(0xFF000000): alpha=255, r=0 → 黑 ✓
   - 白底(0xFFFFFFFF): alpha=255, r=255 → 白 ✓
   - 用 `>>>` 无符号右移提取 alpha，避免有符号右移的负数问题
2. Canvas 创建改用无参构造 + `setBitmap(bitmap)`（`Canvas(Bitmap)` 构造从 API 28 起废弃）
3. 填白改用 `drawRect(0,0,w,h,paint)` + Paint（比 drawColor 更可靠）
4. getPixel 返回值验证 `typeof === 'number'`，非数字按白处理
5. 全黑/全白保护：`blackCount === total` 或 `blackCount === 0` 时返回 error 降级
6. 加详细日志：第一个像素的 ARGB 值、drawText 参数

**待用户实测**：打印后看三种可能：
- 中文正常 → 修复到位
- 空白（不是黑条）→ drawText 没生效，考虑用 webview 渲染
- 还是黑条 → getPixel 返回值异常，考虑用 getPixels 批量读取

## 位图全白 bug 第五次修复（getPixel 类型转换 + 不填白）

**用户复测**：日志显示 `bitmap 144x58, black=0, white=8352, filled=true`，**drawText 调用没抛异常但没有 `first pixel` 日志**——说明 getPixel 在 (0,0) 就走 `continue` 分支，8352 个像素全部判白。

**根因排查**：`typeof pixel !== 'number'` 检查挡掉所有像素。plus.android.invoke 返回 int 时可能不是 JS number（字符串 / Java Integer 对象包装），typeof 检查会让全部像素被判白。

**修复**（`utils/cjkBitmap.js`）：
1. 加 `toNum(v)` 统一类型转换函数：number 直返、string 用 parseInt、Java Integer 对象调 `intValue()`。reflect check、getPixel probe、二值化循环全部走 `toNum`
2. **移除填白步骤**：之前用 `setColor(WHITE) → drawRect → setColor(BLACK)` 切 paint 颜色，plus.android 反射下第二次 setColor 可能静默失效导致白字画白底。透明像素 alpha=0 在 alpha 判断下直接判白，不需要白底
3. paint 颜色始终黑色：createPaint 里 setColor(BLACK) 一次后不再切换
4. 加 `reflect check`：循环前用 `bitmap.getWidth/getHeight + paint.getColor` 验证反射是否工作，能看到 bitmap 尺寸和 paint 当前颜色
5. 加 `getPixel probe (0,0)`：单独测试 getPixel 反射，绕开循环里被吞的异常
6. 加 `getPixelFailCount + firstErr`：循环里统计失败次数和第一次错误
7. 加 `first raw pixel type` 日志：第一次拿到 raw 像素时记录原始 typeof

**wrapText 优化**：连续 ASCII 可见字符 `[\x21-\x7E]` 作为整体 token 处理，避免把 "(TY)" 切成 "T" + "Y)"。之前 "直流控制板(TY)" 被切成 "直流控制板(T" + "Y)"，现在会切成 "直流控制板" + "(TY)"。

## 位图全白 bug 第七次修复（JS Function.prototype.valueOf 名称冲突）

**用户复测**：日志显示 `config=function(nocreate) { this.__UUID__ = plus.tools.UUID('JSB'); ... }`，**config 不是 ARGB_8888 枚举实例，而是 Class 代理 function 本身**。`bitmap is null after createBitmap, 静态方法调用失败`。

**真正根因**：`C.BitmapConfig.valueOf('ARGB_8888')` 这个调用被 **JS Function.prototype.valueOf 拦截**了！
- `plus.android.importClass('android.graphics.Bitmap$Config')` 返回的是 JS function（Class 代理）
- JS function 自带 `valueOf` 方法（Function.prototype.valueOf，返回 this）
- 访问 `C.BitmapConfig.valueOf` 拿到的是 JS 原生 valueOf，不是 Java 静态方法 valueOf
- 调用后返回 `C.BitmapConfig` 本身（function），不是 ARGB_8888 枚举实例
- 传给 createBitmap 时 Java 反射发现类型不匹配，返回 null

**为什么 zebraPrinter 里 `BluetoothAdapter.getDefaultAdapter()` 和 `UUID.fromString()` 能工作**：`getDefaultAdapter`、`fromString` 这些名字不和 JS 原生方法冲突。但 `valueOf`、`toString` 这些名字和 JS Function 原生方法冲突，会被拦截。

**修复**（`utils/cjkBitmap.js`）：
1. **getArgbConfig 改用 `plus.android.getAttribute(C.BitmapConfig, 'ARGB_8888')`** 获取静态字段，绕开 valueOf 名称冲突
2. **getPaintAlign 同样改用 `plus.android.getAttribute`** 获取 Paint.Align.LEFT/CENTER/RIGHT 静态字段
3. 加三层备用方案：
   - 方式 1：`getAttribute(C.BitmapConfig, 'ARGB_8888')`（首选）
   - 方式 2：`plus.android.invoke(C.BitmapConfig, 'valueOf', 'ARGB_8888')`（反射调用，可能返回 null）
   - 方式 3：`getAttribute(C.BitmapConfig, 'RGB_565')`（降级枚举）
4. 缓存判断排除 function 类型：`if (_argbConfig && typeof _argbConfig !== 'function')` 避免缓存错误的 Class 代理
5. createBitmap 调用前加 typeof 安全检查：`config` 必须是 Java 对象，不能是 function

**关键经验（5+ App plus.android 反射陷阱）**：
- ✅ 静态方法用 `Class.method(args)` 直接调用（如 `C.Bitmap.createBitmap`）
- ✅ 实例方法用 `inv(obj, method, args)` 即 `plus.android.invoke(obj, method, args)`
- ✅ 静态字段用 `plus.android.getAttribute(Class, 'FieldName')`
- ❌ **不能用 `Class.valueOf('NAME')`** —— JS Function.prototype.valueOf 会拦截
- ❌ **不能用 `Class.toString()`** —— JS Function.prototype.toString 会拦截
- 名字和 JS Function 原生方法（valueOf、toString、constructor、apply、call、bind、prototype）冲突的 Java 静态方法都要绕开

**待用户复测**：日志关键看：
- `getArgbConfig via getAttribute: type=object str=ARGB_8888`（type 必须是 object，不能是 function）
- `createBitmap: config.type=object`
- `bitmap created: null=false`
- `reflect check: bitmap=144x58`
- `bitmap WxH black=N white=N getPixelFails=0`（drawText 生效的话 black > 0）

## 位图全白 bug 第八次修复（getAttribute 也拿不到静态字段）

**用户复测**：日志显示三种方式都返回 null：
```
getArgbConfig via getAttribute: type=object str=null
getArgbConfig via invoke valueOf: type=object str=null
getArgbConfig fallback RGB_565: type=object
createBitmap: config.type=object config=null
config 无效（type=object），createBitmap 会返回 null
```

**关键诊断**：`type=object str=null` 这两个信息结合揭示了一个 JavaScript 经典坑——**`typeof null === 'object'`**！getAttribute 返回的实际就是 null，但 typeof 报告 object 容易误导诊断方向。

**根因升级**：`plus.android.getAttribute` 在 5+ App 反射模式下**拿不到静态字段**（getAttribute 似乎是为实例属性设计的，不是静态字段）。三种方式（getAttribute with Class、getAttribute with string、invoke valueOf）全部失败。

**修复**（`utils/cjkBitmap.js`）：
1. **方式 1 改为直接字段访问 `C.BitmapConfig.ARGB_8888`**（最可能成功）
   - 类比 zebraPrinter.js 里 `UUID.fromString()` 的直接调用方式
   - `ARGB_8888` 不是 JS Function 原型方法名，不会被拦截
2. 保留 getAttribute / invoke valueOf / RGB_565 / ALPHA_8 作为备用方式
3. 每种方式都打印 `isNull` 和 `isFunc` 字段，方便区分：

   - object（真正的 Java 枚举实例，有效）
4. **getPaintAlign 同样改为直接字段访问 `C.PaintAlign.CENTER`**

**如果所有方式都失败的备用方案**（待用户复测后决定是否实施）：
- 方案 A：用 `plus.graphics.Bitmap`（HTML5+ 官方 API）

## 位图清晰度优化（超采样 + 加粗 + 抗锯齿）

**用户反馈**："我是 20*15mm 字体必须小，不清晰"。ZR668 是 203dpi，20mm 宽只有 160 dots，15mm 高只有 120 dots，小字号中文位图渲染清晰度有物理上限。

**优化方案**（`utils/cjkBitmap.js` + `utils/zplTemplate.js`）：

1. **超采样（Supersampling）**——核心优化
   - `renderTextToGfa` 加 `superSample` 参数（默认 2）
   - 在 ss 倍分辨率渲染（如 2x = 320×240 dots），字号也 ×ss
   - 用 Android `Bitmap.createScaledBitmap(bitmap, w, h, true)` 降采样到目标尺寸
   - 双线性插值让抗锯齿边缘的灰度信息正确量化为黑白
   - 读取像素仍在目标尺寸（性能不变），但边缘更圆润、细笔画不丢失

2. **加粗默认开启**
   - `zplTemplate.js` 调用时 `bold: el.bold !== undefined ? el.bold : true`
   - 203dpi 下细笔画容易丢失，加粗让笔画更结实

3. **抗锯齿条件开启**
   - `createPaint(fontH, bold, antiAlias)` 加第三个参数
   - 超采样模式（ss > 1）下 `setAntiAlias(true)`，让高分辨率渲染有灰度边缘
   - 1x 模式下保持 `setAntiAlias(false)`（二值化下抗锯齿反而糊）

4. **字号自适应超采样倍数**
   - `h <= 16` 用 3x 超采样（极小字号）
   - `h <= 24` 用 2x 超采样（小字号）
   - `h > 24` 用 1x（大字号不需要）
   - 在 `zplTemplate.js` 调用处计算

5. **Paint.setSubpixelText(true)**
   - 亚像素渲染，对位图二值化也有帮助

**关键限制**：203dpi + 16 dots 字号的中文，物理分辨率上限就在那。超采样能改善边缘锯齿，但不能突破物理分辨率。如需更清晰，唯一出路是换 300dpi 打印机（如 IB-PTM7330）。

**待用户复测**：
- Config 问题是否解决（上次日志 try1 direct ARGB_8888 还没看结果）
- 超采样后清晰度是否改善
- 性能是否可接受（2x 超采样约 4 倍内存，但读取像素不变）

## ZR668 TTF 字体灌入 + 项目代码适配

**背景**：ZR668 出厂无中文字体，之前走位图渲染（慢、不清晰）。用户下载了 NOTOMRJ.TTF 字体文件，要通过 USB 把字体灌入打印机 Flash 内存，让中文走 `^A@` 原生渲染。

**字体灌入过程**（PC 端 Python + win32print）：
1. **发现 CISDF 包装**：下载的 NOTOMRJ.TTF 不是标准 TTF，前 49 字节是 Zebra CISDF 头（`! CISDFCRC16\r\nF0E6\r\nNOTOMRJ.TTF\r\n01169550\r\n6016\r\n`），真正的 TTF 数据从第 49 字节开始（`00 01 00 00` TrueType magic）
2. **剥离 CISDF 头**：提取 offset=49 之后的数据，保存为纯 TTF
3. **字体裁剪**：用 fonttools 的 Subsetter，保留 GB2312 全部汉字 + ASCII + 常用符号，从 17.4MB 裁到 1.79MB（7550 字）
4. **~DY 命令下载**：`~DYE:NOTOMRJ,TTF,B,B,<size>,0,0\n` + 二进制数据，通过 win32print 分块（64KB）发送到 `ZDesigner ZR668 Plus (ZPL)2`（USB002 端口）
   - 关键：~DY 的 filename 不带扩展名（`NOTOMRJ` 不是 `NOTOMRJ.TTF`），扩展名在 extension 字段
   - ZR668 支持 TrueType 字体，`^A@N,h,w,E:NOTOMRJ.TTF` 正常工作

**项目代码修改**：

### zebraPrinter.js
- 新增 `_hasTtfFont` 缓存变量 + `TTF_FONT_NAME = 'NOTOMRJ'` 常量
- 新增 `listTtfFonts()` — 查询 `^HWE:*.TTF`（原 `listPrinterFonts()` 只查 `*.FNT`）
- 新增 `checkTtfFont()` — 检测 NOTOMRJ 是否在 E: 盘

- 新增 `hasTtfFont()` / `getCjkFontPath()` — 同步读缓存，返回最佳字体路径

### zplTemplate.js

  - `if (cjk && printer.hasTtfFont())` → `^A@` + `getCjkFontPath()` + `^FB` 自动换行
  - 原 `if (cjk && isBitmapSupported() && !printer.hasCjkFont())` → 位图渲染（后备）
  - 降级 `^A@ E:GB18030.FNT`

## PDA 蓝牙查不到 TTF 字体的问题

**现象**：PDA 蓝牙连接 ZR668 后，`^HWE:*.TTF` 返回 18 行但 `/NOTOMRJ/i` 不匹配，`_hasTtfFont = false`。USB 测试打印中文正常，说明字体确实在 Flash 里。

**可能原因**：
1. ZR668 的 `^HW` 命令不支持 `*.TTF` 通配符过滤，返回的是全盘文件而非 TTF 专用列表
2. `~DY` 下载命令参数格式有误（`~DYE:NOTOMRJ,TTF,B,B,size,0,0` 多了一个 B），可能导致文件名/属性异常
3. 蓝牙 SPP 响应读取不完整或时序问题

**解决方案**：
1. `checkTtfFont()` 增加调试日志：`JSON.stringify(fonts)` 打印实际返回内容
2. 增加 `~HD` 全盘列表作为后备查询（5s 超时）
3. 新增 `force_ttf_font` storage 开关 + `setForceTtf()/getForceTtf()` 方法
4. `hasTtfFont()` 优先检查 `force_ttf_font`，为 true 直接返回 true，绕过蓝牙检测
5. 打印设置页新增"强制TTF字体"按钮，用户手动开启后中文走 `^A@ E:NOTOMRJ.TTF` 原生渲染

### 根因找到：ZR668 自带 HANS.TTF

调试日志显示 `^HWE:*.TTF` 返回的 18 行里有 `E:HANS.TTF 19163928`（19MB）——这就是**打印机自带的中文字体**（HANS = 简体中文）。

之前以为 ZR668 没有中文字体，是因为只查了 `^HWE:*.FNT`（位图字体），没查 `^HWE:*.TTF`（TrueType 字体）。`NOTOMRJ.TTF` 不在列表里，说明 USB 下载实际没存进去（`~DY` 参数多了一个 B），测试打印能出中文是打印机找不到指定字体时自动回退到 `HANS.TTF`。

**最终方案**（不需要下载任何字体）：
- `CJK_TTF_NAMES = ['HANS', 'HANT', 'NOTOMRJ']` — 优先级匹配
- `checkTtfFont()` 遍历列表，找到 `HANS` 即 `_hasTtfFont = true, _ttfFontName = 'HANS'`
- `getCjkFontPath()` 返回 `E:HANS.TTF`
- "强制TTF字体"按钮保留作为后备，但自动检测已能正常工作
