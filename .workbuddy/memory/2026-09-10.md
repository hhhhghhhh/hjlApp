## 打印合批（LPAPI 一次任务多页）— 已落地并验证
- **需求**：批量打印时每个 SN 都是独立任务（N 次蓝牙往返 + 每条硬等 300ms），太慢；要整体打印。
- **根因**：`snPrintList.startPrint` 的 `for` 循环逐条 `printTemplate`，每条一次完整 startJob+commitJob。
- **SDK 依据**（从 `uni_modules/dothan-lpapi-ble/js_sdk/index.js` 反查）：存在 `drawJob({ jobPages, jobInfo, onPageComplete, onJobComplete })`，`jobPages` 是**页数组**（每页 = DrawItem 数组），SDK 内部逐页 startJob→drawItem→commitJob，最后 `commitAllJobs` 一次提交。另有 `startJob({jsonMode:true})` 使 draw* 自动 push 进 `mJobPage`；`commitAllJobs`/`printPageGroup` 为内部实现。
- **实现**（关键设计——渲染算法零漂移）：
  1. `lpapiTemplate.js` 新增 **`createDrawCollector()`**：返回一个与 LPAPI 实例**同形**的代理（同名 `drawText/draw2DQRCode/draw1DBarcode/drawRectangle/drawLine`），但不绘制、只把 opts 收进数组（并补 `type` 字段）。渲染器 `renderTemplateToLpapi` **一行算法未改**，只是传收集器进去即可收集。`DRAW_TYPES` 映射：drawText→text、draw2DQRCode→2DQRCode、draw1DBarcode→barcode、drawRectangle→rectangle、drawLine→line。
  2. `lpapiAdapter.printTemplateBatch(tpl, records, hooks)`：逐条渲染成 jobPages（`splitText` 从真实 lpapi 挂到收集器上，保证换行行数计算一致），`_prepareCanvas(jobW,h)` 建上下文+同步 canvas 尺寸（**不再自己 startJob**，任务生命周期交给 drawJob），再 `drawJob({jobPages, jobInfo:{width,height,printCopies,colorMode:2}, onPageComplete})`。单条时直接复用单条路径。
  3. `printerManager.printTemplateBatch(tpl, records, hooks)`：**能力探测**——适配器有该方法则合批，否则（Zebra）**自动回退逐条**，行为不变。
  4. `snPrintList.startPrint`：非批次模式走合批、**去掉 300ms 硬延迟**；批次模式（标签不带 SN、每条换变量）仍保持逐条。
- **进度**：`onPageComplete` 把 SDK 页级进度映射回 UI 的 `done/currentSn`；合批失败按整批报错。
- **验证**：真实 `@babel/parser` 校验全部 .vue 通过；Node 端到端 mock——3 页渲染 `MATCH: true`（变量未串页）、offsetX 正确叠加、页对象是纯数组且可 JSON 序列化（无循环引用）。
- **真机实测（09-10 11:20）**：当前 `dothan-lpapi-ble` 插件实例（`lpapiPlugin.getLPAPI()` 单例）**未暴露 `drawJob`**，SDK 源码里 `drawJob` 虽挂在 LPAPI 主类、但内部依赖的 `Context.drawJob` 本版本未实现，真机直接报 `lpapi.drawJob is not a function`，打印完全不出。即 `drawJob` 在当前插件封装/版本下**不可达**。
- **修复（降级）**：`printTemplateBatch` 改为【能力探测 + 连续逐条降级】——`typeof lpapi.drawJob === 'function'` 为真才走真正的一次任务多页（分支保留在私有方法 `_printTemplateBatchDrawJob` 备查/待 SDK 升级）；否则对每条 record 复用已验证的 `printTemplate` 单页路径连续提交，**不插入人为延迟、单条失败收集到 `fails` 不中断**。外部语义仍是「整体打印」：一次入口、统一 `onPage` 进度、返回 `{okCount,total,fails}`。批次模式本就走 `printTemplate` 逐条，未受影响。
- **速度说明**：降级后底层每条仍是独立蓝牙任务（N 次往返），只是去掉了原 300ms 人为等待；**真正「一次任务多页」提速需 SDK/插件升级暴露 `drawJob`**。

## 打印页自动回连默认打印机的协议缺陷修复（09-10）
- **现象**：用户选过默认打印机，在打印页触发打印时连不上（日志 `createBLEConnection:fail no device` / errCode 10002）。
- **先澄清（重要）**：日志证明**连接确实发起了**且重试充分——SDK 内 5 次 × 适配器 3 轮 = 15 次，全返回 `no device`。这是**打印机侧不可达**（未开机/未进配对模式/被别的设备占用/超出范围/系统配对失效），**不是"没去连"**。
- **但发现两个真实缺陷（已修）**：
  1. **`preflight()` 回连默认打印机时不传协议**：`snPrintList.vue` 原来 `printer.connect(saved.address, saved.name)` 少了第三个参数（`printSetting.vue` 是传的）。不传时 manager 回落 `loadProtocolForAddress(address) || loadProtocol()`，**stage 记录丢失时会取全局默认 `PROTOCOLS.ZEBRA`** → 用 ZPL 适配器去连 LPAPI 打印机。修复：显式传 `printer.getProtocolForAddress(saved.address) || printer.detectProtocolByName(saved.name)`（按 MAC 记忆 → 按蓝牙名推断机型 → 兜底）。
  2. **`printerManager._ensureConnected` 同一问题**：`loadProtocolForAddress(saved.address) || this.getProtocol()` → 中间插入 `detectProtocolByName(saved.name)` 兜底。
  3. 顺带把 **LPAPI 连接失败的错误文案**做成可操作清单（`lpapiAdapter.connect`）：列出开机/配对模式/被占用/距离/系统配对 5 条排查项，并注明"已重试 MAX 轮仍失败"、`statusCode` 与 `no device(10002)` 含义，避免用户误以为程序没去连。
  4. `preflight` 的 connect 失败也包了一层带排查清单的错误提示。
- 三处改动语法校验通过（2 个 js + 1 个 vue）。

## 首张打印偏移修复（canvas 预热）— 09-10
- **现象**：LPAPI 打印"第一张明显偏移（用户描述为『打外』，明确是**上下偏移**），之后正常"。
- **根因**：`lpapi-uniplugin.initDrawContext` 把绘制上下文**按 canvasId 缓存**（`contexts[canvasId]`）。页面隐藏 canvas 的 `:style` 初始写死 **590x354px**（50x30mm@300dpi 假想值），而真实任务尺寸是"铺满打印头"算出的（PTM230X 48.8mm@300dpi≈576px 宽）。**首次 startJob 用错误尺寸的 canvas 建缓冲 → 首张按错误高度落位**；第二张起因 `emitCanvasSize` 已把 `:style` 改成真实值、ctx 被复用而恢复正常。与用户「第一张偏、后面正常」的观察精确吻合。
- **修复（用户选"打印前预热 canvas"）**：`lpapiAdapter.js`
  - 新增 `this._primedSig = null`（构造函数）：null=未预热，字符串=已预热到的 `pxW x pxH` 签名。
  - 新增 `async _primeCanvas(wMm, hMm)`：签名相同则直接 return（不产生额外等待）；否则 `ensureDrawContext()` → `emitCanvasSize(pxW,pxH)` → **`delay(260)`**（比常规 120ms 长，给首次完整的 响应式→重排→SDK 读节点 链路留时间）→ 记签名。
  - `printTemplate`：`setLabelSize` 后、`_startJob` 前调 `await this._primeCanvas(jobW, heightMm)`。
  - `_prepareCanvas`（合批/drawJob 路径）也改走 `_primeCanvas`。
  - `_refreshMediaInfo` 末尾 `this._primedSig = null`：换打印机/介质后 dpi/打印头宽/对齐可能变，预热作废需重做。
- **代价**：单个尺寸首次打印多等约 260ms，之后同尺寸无额外开销。
- **待验证**：真机打一批，确认首张不再偏。**若仍偏**，则不是 canvas 时序而是打印机"首张找间隙"行为（间隙纸首次进纸吐纸定位），需在打印前先空走一张/做传感器校准——App 侧无法通过 canvas 解决。

## 打印「停止」失效修复（09-10）
- **问题**：用户发现点「停止」没用。根因：`cancelPrint()` 只置 `this.canceled=true`，而 `canceled` **只在批次模式的 for 循环里被检查**；非批次走合批路径 `await printer.printTemplateBatch(...)` 一次性交给适配器，中途**完全不检查取消标志**，导致按了也照打。
- **修复（取消信号贯通 hooks）**：新增 `hooks.shouldCancel()` 回调，从页面一路传到适配器逐条循环。
  1. `snPrintList.startPrint`：非批次分支传 `shouldCancel: () => this.canceled`；成功后按适配器回报的 `ret.okCount` 截取 `okList`（取消时 okCount < 总数），并读 `ret.canceled`。
  2. `lpapiAdapter.printTemplateBatch` 降级循环：每轮开头 `if (hooks.shouldCancel()) { canceled=true; break }`，返回 `{okCount,total,fails,canceled}`。
  3. `printerManager.printTemplateBatch` 的 Zebra 回退循环同样加检查并返回 `canceled`。
  4. `cancelPrint()` 加即时 toast「正在停止，已发出的标签仍会印出」，避免用户以为按钮坏了。
- **语义边界（重要）**：蓝牙是"发出即返回"，**已经下发给打印机的那一条无法撤回**；停止只保证"后续未发的记录不再发"。这与组件里原有的提示文案一致。
- 验证：Node 端到端复刻循环——第 3 条时置 canceled，第 4 条发完后中断，`okCount:4/10 PASS`。
